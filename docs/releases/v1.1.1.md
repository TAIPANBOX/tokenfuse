# TokenFuse 1.1.1

This release fixes the gateway's throughput ceiling (#319). Under concurrent
load the gateway used about one core, slowed down the longer it ran, and at
50 agents and more its fail-closed policy check started refusing legitimate
calls. The cause was the semantic response cache, which ran in `shadow` mode
by default and did work proportional to everything it had ever stored on
every call. The frozen names in `compat/1.0.json` do not change. The umbrella
crate and both client SDKs move to 1.1.1 with no client behavior change.

## Changed

- **The semantic cache is off unless you turn it on (#326, invariant 63).**
  `TOKENFUSE_CACHE` unset, empty or `off` now means off; `shadow` and `on`
  are unchanged; any other value is off with one warn line naming it. The
  gateway logs the mode it resolved at startup (`semantic cache
  cache_mode=Off`). Until 1.1.0 an unset variable meant `shadow`: every
  eligible call was compared against the stored entries and then stored,
  which is what produced the ceiling, whether or not anyone had asked for
  the cache.

## Fixed

- **The cache no longer walks everything it holds under one lock (#327,
  invariant 64).** A repeated request is found through an exact-match index
  in constant time, and is served only after the SHA-256 of its text matches
  the stored one, so a hash collision can never return another request's
  answer. A repeated request refreshes its entry instead of adding another.
  Expiry and eviction are amortised constant time, lookups take a read lock
  and no longer block each other, and the similarity walk for a new request
  runs over contiguous memory. At 10,000 entries per partition: a repeat
  lookup 79.8 us to 0.63 us, a miss 83.9 us to 72.1 us, a store 29.9 us to
  3.8 us.

## Measured

On one 4-core Intel N150 box, the single-machine install's gateway, a mock
upstream (latency and refusals real, money invented) and one identical
prompt, the cache's worst case before this release:

| agents | 1.0.4 (cache defaulted to shadow) | this release, nothing set | this release, `TOKENFUSE_CACHE=shadow` |
|---|---|---|---|
| 50 | 183 calls/s, 4 refused | 1096 calls/s, none refused | 1099 calls/s, none refused |
| 100 | 119 calls/s, 46% refused | 1987 calls/s, none refused | 1928 calls/s, none refused |

The same ten-agent load run three times afterwards gave 110, 112 and 107
calls/s on 1.0.4 and 223 calls/s each time on this release.

## Upgrade notes and limits

- If you relied on `shadow` for the would-hit counts, set
  `TOKENFUSE_CACHE=shadow` explicitly; it now costs nothing measurable at
  the load above.
- The single-machine, Kubernetes and development launchers set
  `TOKENFUSE_CACHE=off` explicitly on their `main` branches, which avoids the
  ceiling whatever gateway version they install; their next tags carry that
  and pin this release.
- The measurements above used one prompt on one box. Varied prompts and a
  real provider behind the gateway are measured separately and reported
  with the launchers that pin this release.
