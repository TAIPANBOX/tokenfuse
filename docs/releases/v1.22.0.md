# TokenFuse 1.22.0

A minor release. A run's label now reaches the OpenAI wire and the fetch plane, the MCP broker follows no redirect, and a call whose usage stops short is charged what it cost rather than what its opening counters said.

It covers everything merged since v1.21.0: pull requests #503 to #508. Pull requests #503 to #505 moved the README and the compose pins to v1.21.0 after that tag existed. `compat/1.0.json` and `components.json` do not change.

## Upgrade

Read this section before you change the image tag.

1. No migration. Change the image tag.
2. **The MCP broker follows no redirect.** An upstream, a delegation key set or a revocation list reached through a URL that answers 301, 302, 307 or 308 now fails, with `upstream error: answered ...` for an upstream. Point the setting at the final URL. A trailing slash is the usual cause.
3. **A call on the OpenAI door that searched now labels its run.** A `url_citation` in an answer reads as `web_search`, so a run that went on to ask for a shell can now be refused where it was not before. The record is the existing `taint_raised` event.
4. **A classified upstream is told the run.** The forwarded `tools/call` carries `x-fuse-run-id`, for an upstream in `TOKENFUSE_MCP_UPSTREAM_LABELS` and no other. Scopyx 1.3.0 reads it. Nothing else of the caller's is forwarded.
5. **A body that stopped short costs more than it did.** It is charged the input side as reported and the output side at the request's cap, so a figure you compare across this release can rise. The cost basis is the new `PartialUsage`, and the FOCUS row is labelled `estimated`, because it carries no token counts. A refusal gets no cap.

## Security

- **The broker's client followed redirects (#506).** A 307 keeps the body, which by then held the secrets the broker wrote into it, and reqwest strips only five headers on a cross-host redirect. An upstream that answered with one could have had those secrets sent to any host it named. `mcpbroker::upstream_client` follows none, and a 3xx is an upstream error whatever its body reads like. It was the last client in this repository that followed them.
- **A tool call in a closing `message` chunk reached the client unheld (#506).** The stream's reader looked only in `delta`, so a call a provider put in a whole `message` at the end of a stream was neither held nor judged. Both are read now.
- `next` 15.5.28 for GHSA-2464-fhr4-w9xw and GHSA-p3m5-59mp-jv5r in the dashboard, and `litellm` 1.100.4 for GHSA-7hp6-4w63-5g45 in one recipe (#507).

## Added

- **The OpenAI wire's search labels the run (#506, invariant 143).** That wire records a search the provider ran as a citation and no tool block. `provider_tools_in` reads `choices[].message.annotations[]`, once per answer, and the stream reads the same from `delta` and a closing `message`, before the bytes go out, so a client that leaves early does not leave the label behind.
- **A fetch joins its run (#506).** See Upgrade, item 4. A plane that records what it serves now joins its record to the run that asked.

## Fixed

- **A stream that ended cleanly without its final usage event settled on the opening counters (#508, closes #308).** The output the provider generated cost the run nothing. `ParsedUsage::complete` says whether the provider's last word on usage arrived.
- **Usage that had arrived before a body broke was dropped (#508, closes #309).** `HttpProvider::send` now publishes what the parser holds, so a break after the final event settles as reported. The two are one change, because publishing on the error path alone would have settled a body broken after `message_start` on its opening counters.
