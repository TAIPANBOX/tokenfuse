# TokenFuse 1.17.0

A minor release that makes the MCP broker publish the protected resource metadata the MCP authorization specification requires, whenever the agent-token door is on. It adds a helper that lets Python and JavaScript agents answer DPoP nonce challenges. The delegation key set can now be polled from a URL, so removing an issuer key no longer waits for a restart.

It covers everything merged since v1.16.0: pull requests #455 (the v1.16.0 badge and pins), #456, #457 and #458. Two of them change what the broker answers at startup and to a refused agent token. The **Breaking** and **Migration** sections say which deployments are affected. Read them before upgrading.

This is a minor, not a major: no frozen name in `compat/1.0.json` is removed or renamed, and every change to the surface is an addition. The changes alter two startup refusals and the body and challenge a refused agent token receives at the MCP broker. They do not alter the names of the surface.

## Added

- **A helper for agent tokens in Python and JavaScript (#457).** `tokenfuse.agent.AgentAuth`, an `httpx.Auth`, and `createAgentFetch` in JavaScript obtain an agent token from vouchryx with DPoP, cache it, and refresh it at 80 percent of its life. Each request carries `Authorization: DPoP` and a fresh proof with `ath`. A server's `use_dpop_nonce` challenge is answered once, with the newest `DPoP-Nonce` the server sent (RFC 9449 sections 8 and 9). The Python base package stays dependency-free. The helper is the optional extra `tokenfuse-sdk[agent]`, which adds httpx and cryptography.
- **The delegation key set can be polled from a URL (#458).** `TOKENFUSE_DELEGATION_JWKS_URL` names an absolute http or https key set that the delegation door polls. `TOKENFUSE_DELEGATION_JWKS_INTERVAL_MS` sets the interval, 60 seconds by default. It needs `TOKENFUSE_DELEGATION_ISSUER`, and it is mutually exclusive with the file form, `TOKENFUSE_DELEGATION_JWKS`, which is unchanged. The first fetch must succeed, or the process exits 2 before it listens.

## Fixed

- **The broker publishes the protected resource metadata for the agent-token door (#456).** The MCP authorization specification (revision 2026-07-28) requires an MCP server to publish RFC 9728 metadata. The broker published it only with XAA on, and a refused agent token named no document in its challenge. With `TOKENFUSE_AGENT_TOKENS` on, the broker now serves the document at `/.well-known/oauth-protected-resource`, and at the path-suffixed twin of its resource's own path. The URL in the challenge is built from the configured resource, never from a `Host` header.
- **Removing an issuer key no longer waits for a restart of each door (#458).** The key set was read once at startup, so a key the issuer withdrew kept verifying until a restart. With `TOKENFUSE_DELEGATION_JWKS_URL` set, a successful poll replaces the held set, so a removed key stops verifying at that poll. An unknown `kid` is refused even when the one key held would verify the signature. A failed poll, or a body that is not a usable key set, keeps the keys already held.

## Breaking

Each item says what changes for an existing deployment. Items 1 and 2 apply only when the operator sets the variables named.

1. **An agent audience that is not an https URL refuses to start (#456, only with the agent-token door on in the MCP broker).** `TOKENFUSE_DELEGATION_AUDIENCE` must be an absolute https URL with a host, no query or fragment, and printable ASCII without a double quote or a backslash. An opaque name such as `tokenfuse-broker` now makes `tokenfuse mcp-broker` exit 2 at startup and names the variable. Before this release the broker started.
2. **XAA and the agent door must name the same resource (#456, only with both doors on).** When `TOKENFUSE_MCP_RESOURCE` and `TOKENFUSE_DELEGATION_AUDIENCE` are both set and differ, the broker exits 2 and names both variables.
3. **A refused agent token gets the agent door's own answer at the broker (#456).** The body is the agent door's: `error.type` is `agent_token_refused` for a presented token that does not verify, and `agent_token_required` for a call with no credential under `require`. The `WWW-Authenticate` header is a DPoP challenge that names the protected resource document. `error="invalid_token"` appears only for a presented token. Before this release the body was the generic unauthorized body, and with XAA on the challenge was Bearer. The status stays 401. With XAA on and `require`, a call with no credential gets the DPoP challenge and the agent body.

## Migration

- **Audience (#456).** Make the audience an https URL, and have vouchryx mint agent tokens for that same URL, because the door checks `aud` exactly. A token minted for the old value stops verifying once the audience changes, so change both in one restart window.
- **XAA resource (#456).** Set `TOKENFUSE_MCP_RESOURCE` and `TOKENFUSE_DELEGATION_AUDIENCE` to the same URL, or unset `TOKENFUSE_MCP_ACCEPT_XAA`.
- **Clients of the broker (#456).** A client that matched the generic body's type, or read `WWW-Authenticate` as Bearer, should match the agent door's `error.type` and read the DPoP challenge. The status code did not change.
- **The key set from a URL (#458).** Nothing to do unless you adopt it. Setting both `TOKENFUSE_DELEGATION_JWKS` and `TOKENFUSE_DELEGATION_JWKS_URL` exits 2.

## Upgrade

Replace the image tag with `v1.17.0`, or use the release binary. Before the upgrade, check each deployment against the Breaking cases above. What an operator will see on upgrade:

- An MCP broker with the agent-token door on and an agent audience that is not an https URL exits at startup, with a message that names `TOKENFUSE_DELEGATION_AUDIENCE`.
- A broker with XAA on and a different agent audience exits at startup, with a message that names both resource variables.
- `GET /.well-known/oauth-protected-resource` answers 200 on a broker with the agent-token door on, and 404 with both doors off.

The README examples, the release badge and the compose image pins move to `v1.17.0` in a follow-up change after the tag, as they did for v1.16.0, so this release changes no README or compose file.

## Not proven

- No MCP client conforming to the 2026-07-28 revision was run against the broker. The tests check the document and the challenge against the text of RFC 9728 and RFC 6750.
- No live vouchryx token reached the agent-token door, and no live authorization server was asked for the metadata. The tests mint tokens the way vouchryx mints them.
- The SDK helpers were tested against a stub vouchryx and a stub door in their own test files. No live server with DPoP nonces turned on was run.
- The poll interval and the time from a key's removal at the issuer to its first refusal were not measured against a live vouchryx. A held key set has no age limit, so a removed key keeps verifying while the issuer is unreachable.
- The replay caches for agent-token proofs and the run-owner claims are per process, as in v1.16.0.
- The Rust build and test run is CI's.
