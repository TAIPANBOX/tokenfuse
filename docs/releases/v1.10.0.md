# TokenFuse 1.10.0

A retained call and its closure now reach the event bus, and the MCP broker
waits long enough for a policy decision that takes more than 50 ms.
- A call whose outcome became unknown writes one `call_retained` (medium), so a
  notifier can tell a person that money is waiting for them.
- A person closing a retained reservation writes one `retained_closed` (high),
  so the record holds the closure beside the console's own command record.
- The tool path's deadline for the policy plane defaults to 1000 ms. A deny
  that took longer than 50 ms used to arrive after the broker had given up,
  and the default failmode then let the denied call through.

This is a minor release because it adds two agent-event types, appended after
`run_stalled` in `contracts/tokenfuse-constants.json`, and changes a default
that no frozen name describes. Nothing is renamed or removed, and nothing
frozen in `compat/1.0.json` moves. The umbrella crate and both client SDKs move
to 1.10.0 with no client behavior change.

## Added

- **A retained call and its closure reach the bus (#399, invariant 90).**
  - `call_retained` (medium) is written once per reservation the gateway
    retains (invariant 50), after the journal write and the registry push, so
    its `journaled` and `listed` members are facts. `data`: `reservation_id`,
    `amount_microusd`, `unit`, `model`, `journaled`, `listed`. The startup
    replay restores reservations without writing it again.
  - `retained_closed` (high) is written once per applied closure (invariant
    89), after the closure record is synced, the money settled and the Cloud
    row written. `data`: `reservation_id`, `revision`, `operation_id`,
    `evidence_kind`, `settled_microusd`, `evidence_ref`, `unit`. A refused
    attempt and a replay of an applied operation write none. Who closed it is
    in the console's `console_command`, joined by `reservation_id`.
  - Both are registered in agent-passport's SPEC 6.2 (agent-passport#74),
    mapped by trailryx's record plane (trailryx#94) and described by heraldyx
    (heraldyx#95). They are written only with `TOKENFUSE_EVENTS_PATH` set, as
    every event is.

## Fixed

- **The MCP broker waits 1000 ms for the policy plane by default (#398,
  invariant 74).** On the tool path (a decide that carries a `tool_call`) the
  deadline is now `TOKENFUSE_MCP_WARDRYX_TIMEOUT_MS` if set and usable, else
  `TOKENFUSE_WARDRYX_TIMEOUT_MS` if the operator set it, else 1000 ms. The
  model path keeps 50 ms. Measured on the real broker before the fix: a policy
  plane that answered deny after 120 ms (the ordinary case behind a typed-signal
  proxy, which waits up to 150 ms for its model) was given up on at
  50 ms, the default failmode (open) applied, and the denied tool call was
  forwarded upstream.

## Upgrade

- **Nothing to configure.** The two events are written only where events are
  exported, and both launchers already set every timeout explicitly (the
  gateway 250 ms, the broker 7000 ms with the typed risk proxy), so they keep
  their values.
- **A bare broker with no timeout variables now waits up to 1000 ms** for a
  policy plane that is slow or unreachable, where it waited 50 ms. Set
  `TOKENFUSE_MCP_WARDRYX_TIMEOUT_MS` to choose another figure.
- **A consumer of the bus** sees two new types from source `tokenfuse`. A
  consumer that does not know them ignores them, as SPEC 6.1 requires.

## Not proven

- No live gateway, appliance or real provider was run with this release; the
  events were measured by tests through CI, not on a running stack.
- trailryx and heraldyx were not run against events this binary wrote.
- A call that named no agent in `x-fuse-agent-id` writes neither event, even
  when a proven delegation chain names one; the skip is counted. Both events
  are filed under the same agent for that reason (invariant 90).
- A reservation retained while the export was off, or before this version, is
  never reported.
- The 1000 ms was tested against a stub that denies in 120 ms, not a live
  typed-signal proxy in front of a live wardryx.
