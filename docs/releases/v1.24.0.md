# TokenFuse 1.24.0

A minor release. The MCP broker's `tools/list` answer now leaves out the tools wardryx refuses the calling agent outright, so an agent is no longer shown tools its policy forbids.

It covers everything merged since v1.23.0: pull request #516, which carries the broker change (estate-gates GAPS G3.13). Pull request #518 moved the README and the cloud compose file to v1.23.0 after that tag existed. `compat/1.0.json` and `components.json` do not change, and no environment variable is new.

## Upgrade

Read this section before you change the image tag.

1. No migration. Change the image tag.
2. **`tools/list` through the broker can now be shorter.** With `TOKENFUSE_WARDRYX_MODE=enforce` and a named caller (an `x-fuse-agent-id` header or an agent token), the broker removes from the upstream's listing every tool wardryx refuses that agent with no approval able to lift the refusal: the ones a `deny_tool` rule names, and the ones an `allow_tool` list leaves out. The order of the rest is kept. A client that counted on the full upstream listing sees fewer tools.
3. **A tool with no grant stays listed.** Its call is the one wardryx holds for the owner's approval (`-32004`, with the policy's reason), so narrowing does not take that hold away.
4. **Shadow mode removes nothing.** Under `TOKENFUSE_WARDRYX_MODE=shadow` the listing goes back whole and carries `_tokenfuse.tools_would_hide`, the number of tools enforce would have removed. Use it to measure before you switch to enforce.
5. **A listing that names no agent is unchanged.** stdio, and an HTTP call with neither the header nor an agent token, ask wardryx nothing and get the upstream's listing as it came.

## Security

- **An agent is no longer shown tools its policy refuses outright (#516, invariant 146).** After the poisoning and rug-pull scans, which still judge the whole listing the upstream sent, the broker asks wardryx `POST /v1/filter-tools` about the listed names, for the same agent id and `mcp:<agent>` run id the `tools/call` gate uses. Only an entry under `deny_tool` or `allow_tool` removes a tool; an entry under no rule, or under a rule the broker does not know, removes nothing. The question goes through the same filter cache as the model path (`TOKENFUSE_WARDRYX_CACHE_TTL_MS`), within the tool path's timeout (`TOKENFUSE_MCP_WARDRYX_TIMEOUT_MS`).
- **When wardryx is unavailable or errs, the list is left whole, in every failmode, with a warn line.** `TOKENFUSE_WARDRYX_FAILMODE` still decides every `tools/call` at the gate, which stays the security boundary; a listing is what an agent is shown. A 404 from a wardryx that predates the route is warned once per process, any other failure each time, and a failure is never cached.
