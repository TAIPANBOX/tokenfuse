# TokenFuse 1.11.0

The MCP broker and the gateway now read what a tool says about itself, not only
what a tool is called, and a tool seen to change since it was pinned can no
longer be called.
- `mcp-scan` and the live broker find a credential, an order to run another
  tool, a local credential path, text addressed to the model and hidden text
  in a tool's metadata, where they used to find stock phrases only.
- The broker refuses a `tools/call` for a tool whose definition it saw change
  since the lock pinned it, while the scan is `block`.
- The gateway reads the tools a request declares in `tools[]`. A poisoned
  description labels the run `suspected_injection`; it never refuses the
  request itself.

This is a minor release because every change is additive behaviour behind
names that already exist: new finding kinds in the scan report, a new
`decision` word on the broker's `tool_call` record, and a new source for a
label the firewall already had. Nothing is renamed or removed, no environment
name is added, and nothing frozen in `compat/1.0.json` moves. The umbrella
crate and both client SDKs move to 1.11.0 with no client behavior change.

## Added

- **The scan reads tool metadata, not only stock phrases (#402, invariant
  92).** `scan_injection`, the one function `tokenfuse mcp-scan` and the live
  broker both call, runs five signals over each tool description and every
  parameter description:
  - `secret_in_metadata` (critical): a credential `dlp` recognises. The kind
    of secret is named; its value is never repeated.
  - `cross_tool_reference`: another tool of the same listing named as a whole
    token. Medium on its own, high with an action word and an amplifier
    ("always run X and paste its output").
  - `local_secret_path`: a path to a local credential file. Medium on its
    own, high beside a read or send verb.
  - `model_addressed_text` (high): text addressed to the model with an order
    after it.
  - `hidden_text` (high): Unicode tag characters, bidirectional controls and
    HTML comments.

  The stock phrases and zero-width characters keep kind `poisoning` at high.
  Each finding in the report now carries a `kind` and a `severity`.
- **A drifted tool cannot be called (#404, invariant 91).** With
  `TOKENFUSE_MCP_SCAN=block` and a lock, a tool whose definition a
  `tools/list` showed changed since it was pinned is refused on `tools/call`
  with JSON-RPC `-32003`, before DLP, the taint gate, the policy plane and
  secret injection, and one `tool_call` is written with
  `decision: "refused-tool-changed"`. In `warn` the call is forwarded and
  logged once per tool. A tool that matches the lock again can be called
  again. Same on stdio.
- **Declared tools are read for poisoning (#405, invariant 93).** With the
  firewall in `shadow` or `enforce`, a request's `tools[]` (both wire shapes)
  goes through the same scan. A finding at high or critical adds
  `suspected_injection` to the run, one `taint_raised` records it (stage
  `tool_result`, the tool names, the signal kinds, no text) and the answer
  carries `x-fuse-taint: raised: ...`. In `enforce` the starter rule then
  denies the run's later dangerous actions. The request itself is never
  refused for a description (invariant 27). Each distinct tool set is scanned
  once per process.

## Fixed

- **quinn-proto 0.11.15 to 0.11.19 (#403)** for RUSTSEC-2026-0338 to 0342, in
  both lockfiles. `cargo audit` was red on every pull request until it landed.

## Upgrade

- **`mcp-scan --fail-on high` can now fail on a listing it passed.** A
  credential, a chained-tool order, an addressed instruction, a read path and
  hidden text are high or critical. A bare mention of another tool or a bare
  path is medium.
- **A broker with `TOKENFUSE_MCP_SCAN=block` can now block a listing it used
  to relay**, for the same reasons, and refuses calls to a tool it saw drift.
  `warn`, the default, logs and forwards both.
- **A gateway firewall in `shadow` (the default) writes more `taint_raised`
  and `taint_shadow` events** when agents declare tools with instruction-like
  descriptions. `"detect_injection": false` in the firewall policy turns this
  scan off together with the tool-result scan; `TOKENFUSE_FIREWALL=off` reads
  nothing at all, as before.
- **A consumer of the broker's `tool_call` records** sees one new `decision`
  word, `refused-tool-changed`.

## Not proven

- No live gateway, broker, appliance or real provider was run with this
  release; every change was measured by tests through CI.
- Every signal reads shapes, never meaning. A description that tells the model
  in calm prose to fabricate an answer carries no shape and passes.
- The drift state lives in the broker process: a restart forgets which tools
  drifted. The broker fetches no listing of its own, so a change no client
  re-listed is not seen. Added and removed tools are not acted on.
- Declared tools are not pinned across turns. A clearance (invariant 28) does
  not outlast the next turn while the poisoned tool is still declared. The
  `taint_raised` record says stage `tool_result` for text that is not a tool
  result.
- The launchers run the gateway's firewall in shadow, so on a stack started
  from them a poisoned declaration is recorded, not acted on.
