# TokenFuse 1.15.0

A minor release that closes five agent-security defects in defaults and small fixes, and puts one more kind of finding on the bus. A tool the policy names nowhere is no longer harmless once the run has read untrusted input. An enforcing policy hook fails closed unless an operator chose open. The attestation the policy plane is told comes from the door a call came through, not from a header. The tool-call check needs a client key and answers only about the caller's own runs. A gateway that authenticates nobody and listens beyond loopback says so at startup. A DLP finding the scanner lets through is now an agent event.

It covers everything merged since v1.14.0: the `dlp_shadow` event (#446) and the security wave that closes the defects above (#447). The release changes behaviour in those defaults, so read the **Breaking** section before upgrading.

This is a minor, not a major: no frozen name in `compat/1.0.json` is removed or renamed, and the changes below alter what a call is judged on, not what the surface is called.

## Added

- **A DLP finding the scanner lets through is on the bus as `dlp_shadow` (invariant 114).** One event per scanner, carrying the kinds and their counts and never the matched text. It is written only when neither scanner refused the prompt, so a secret the PII scan then blocks is not reported as let through. Consumers that route on agent-event types see one new type, at `medium`.
- **`GET /healthz?detail=1` reports client authentication and the bind (invariant 119).** It answers the status, whether client keys are configured, whether the bind is loopback, and any warning in force. Plain `GET /healthz` still answers `ok`, unchanged.
- **A startup warning when client authentication is off on a non-loopback bind (invariant 119).** It is printed to stderr and written to the log, and it names the variable that closes it. It is a warning, not a refusal, so deployments that rely on network placement still start.

## Fixed

- **A tool the policy names nowhere is not harmless after untrusted input (invariant 115).** A tool that neither firewall map names exercises the capability `unclassified`. The starter rule `no-exec-after-untrusted` denies it once the run has read untrusted input. A run with no untrusted label behaves exactly as before, and shadow mode records what enforce would have refused. Both the model's tool calls and `/v1/fuse/check-tool-call` judge this the same way.
- **The attestation method the policy plane is told comes from the door (invariant 116).** A call admitted by a verified DPoP proof is attested as `dpop-key`, and every other call as `none`. The caller's `x-fuse-attestation-method` header is ignored, with one log line per process saying so. This holds on the LLM path and at the MCP broker.
- **The tool-call check needs a client key and answers only about the caller's own runs (invariant 118).** With client keys configured, `/v1/fuse/check-tool-call` answers `401` to a caller without a valid key, and answers `deny` with no labels for a run another key opened. The MCP broker asks with its caller's key, and an answer outside 2xx counts as no answer, decided by the taint failmode, never as permission.
- **An enforcing policy hook fails closed when no failmode is set (invariant 117).** Under `TOKENFUSE_WARDRYX_MODE=enforce`, an unset `TOKENFUSE_WARDRYX_FAILMODE` is now `closed`. An explicit `open` still works, and is logged at startup.

## Breaking

Each change below alters a decision a deployment may already depend on. The migration says what to set to keep the old behaviour, or what to check first.

- **Unmapped tools after untrusted input are refused in enforce mode (invariant 115).** A run that carries an untrusted label, for example one that read a web page or a file, and then asks for a tool named in neither firewall map gets `403` with `taint_block`, rule `no-exec-after-untrusted`, denied `unclassified`. A run with no untrusted label is unchanged.
  *Migration:* classify the tool in a `TOKENFUSE_FIREWALL_CONFIG` file, as a source or as a capability. Or run the firewall in shadow first and read the `taint_shadow` events that name `unclassified`. Invariant 96 already names each unmapped tool in the log once per process.
- **`x-fuse-attestation-method` is ignored (invariant 116).** A wardryx policy that uses `deny_if_unattested` now refuses every caller that is not DPoP-proven, client-key callers included. No launcher policy uses that rule today.
  *Migration:* check whether your policy uses `deny_if_unattested`. If it does and your agents authenticate by client key, those agents are now refused, as the rule says.
- **An enforcing hook with no failmode fails closed (invariant 117).** Under `TOKENFUSE_WARDRYX_MODE=enforce`, calls the hook would judge are refused with `403` while wardryx is unreachable. stack-single and stack-k8s already set `closed`. A hand-written deployment that set neither is affected.
  *Migration:* set `TOKENFUSE_WARDRYX_FAILMODE=open` to keep the old behaviour. The startup line names the failmode in force.
- **The tool-call check needs a key when client keys are configured (invariant 118).** An executor that calls `/v1/fuse/check-tool-call` on a gateway with `TOKENFUSE_CLIENT_KEYS` set must send `x-fuse-key`, or receive `401`. A run another key opened is answered `deny` with no labels.
  *Migration:* send the caller's key with every check. Without client keys nothing changes.
- **A non-loopback bind with no client keys prints a warning at startup (invariant 119).** It is a warning only. Plain `/healthz` still answers `ok`.
  *Migration:* none, unless a tool parses the startup output.

## Upgrade

Replace the image tag with `v1.15.0`, or use the release binary. Before the upgrade, work through the Breaking section for each deployment that matches one of its cases.

What an operator will see on upgrade:

- An enforcing gateway with no failmode set refuses calls while its policy hook is unreachable.
- A tool that reads or writes outside both firewall maps is refused after the run has read untrusted input, and shows as `unclassified` in the trace.
- `GET /healthz?detail=1` gains fields. Plain `/healthz` does not change.
- The agent-event stream gains `dlp_shadow` at `medium`.

The README examples, the release badge and the compose image pins move to `v1.15.0` in a follow-up change after the tag, as they did for v1.14.0, so this release changes no README or compose file.

## Not proven

- The CI run on `main` at `5a0ca90` passed, which exercises the integration tests for the defaults above. Those tests run the real binary; nothing here has been run against a live wardryx or a live launcher.
- A classified read tool, such as one that fetches a URL, can still carry data out in its arguments after untrusted input. Anti-exfiltration was not widened.
- An operator's policy file is judged by its own rules. A file that names no rule denying `unclassified` keeps the old behaviour for unmapped tools. No floor was added to it.
- The metered doors still let one client key name a run that another key opened, and a refused call there still says the run's labels in its `403`. A child run that declares another key's run as its parent inherits that run's labels. Binding runs to their keys at the metered door is a separate change.
- wardryx still trusts whatever attestation its enforcement point sends. The field is honest only for calls that pass through this gateway.
- The owner of each run for the tool-call check is held in memory and is lost on restart.
- The rest of the default-profile work, a governed profile and a named observe profile, is not built.
