# TokenFuse 1.1.0

This release adds two things on the policy side of the gateway and fixes how
it reports the policy plane. Everything new is off unless configured. The
frozen names in `compat/1.0.json` do not change; the new names are additive.
The umbrella crate and both client SDKs move to 1.1.0 with no client behavior
change.

## Added

- **Shadow tool pruning (#321, invariant 61).** With
  `TOKENFUSE_TOOLS_PRUNE=shadow` (default `off`), the gateway asks wardryx's
  new `POST /v1/filter-tools` (wardryx 1.1.0) which of the declared tools its
  `deny_tool` rule would refuse, and prices their schemas in estimated input
  tokens. It only measures: the forwarded request is byte-identical whatever
  the setting. The result is in the response header
  `x-fuse-tools-would-prune: <n>;est_tokens=<t>` and in three new nullable
  trace columns (`tools_offered`, `tools_would_prune`,
  `pruned_schema_tokens_est`), which stay empty when nothing was measured. It
  needs the wardryx hook on and an `x-fuse-agent-id` on the request; a wardryx
  without the route is named once in the log and measures nothing.
- **A third door on the MCP broker: a Cross App Access access token (#322,
  invariant 62).** With `TOKENFUSE_MCP_ACCEPT_XAA=on` and
  `TOKENFUSE_MCP_RESOURCE` set, the broker accepts a vouchryx-issued XAA
  bearer access token (draft-ietf-oauth-identity-assertion-authz-grant),
  verified offline against the delegation issuer's key set, and publishes
  RFC 9728 protected-resource metadata. The chain the policy plane is told
  comes from the token's signature, never from a header. It needs
  `TOKENFUSE_DELEGATION_ISSUER`, `TOKENFUSE_DELEGATION_JWKS` and
  `TOKENFUSE_DELEGATION_URL` configured. Both new variables are listed as
  experimental in `compat/1.0.json`, because the grant is still an IETF
  draft.

## Fixed

- **A wardryx answer outside 2xx is reported by its status (#323, invariant
  19).** Before this release the gateway decoded every wardryx answer as a
  decision, so a 400 for a request with no agent id, a 401 for a wrong
  `TOKENFUSE_WARDRYX_KEY` and a 5xx were each logged as a JSON error behind
  "wardryx unreachable". The reason now reads, for example,
  `wardryx answered 401 on /v1/decide: missing or invalid bearer token;
  failmode=Closed applied`, in the log, in the `dependency_failed` event and
  in the 403 an agent gets under enforce. The failmode decides such an answer
  exactly as before, it is never cached, and `/v1/policy-plane` still counts
  it as a fallback, never as a verdict.

## Upgrade notes and limits

- A deployment that sets none of the new variables behaves as 1.0.4 did. The
  three trace columns are appended and nullable, so older trace files still
  read (invariant 6).
- Shadow tool pruning needs wardryx 1.1.0 or later; against an older wardryx
  it logs once and records nothing.
- The XAA door keeps no replay cache, so a captured token works for the rest
  of its lifetime (at most 300 s at vouchryx). The key set is static, so a
  vouchryx key rotation needs a broker restart. The LLM proxy does not accept
  XAA. No real identity provider has been used with it yet; the proving runs
  used vouchryx and local keys.
- heraldyx renders none of an event's `data`, so its mail for a policy plane
  that refused the call still says the plane could not be reached; the
  event's own detail is correct.
- The launchers need their own pin updates; tagging this repository does not
  change a running installation.
- The raft backend is optional and is compiled out of the shipped gateway
  image, as in earlier releases.
