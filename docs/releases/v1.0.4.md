# TokenFuse 1.0.4

This release carries one money-path fix and one security fix, both in how the
gateway sends a call to its provider. The umbrella crate and both client SDKs
move to 1.0.4 with no client behavior change. The frozen names in
`compat/1.0.json` do not change.

## Fixed

- The provider client no longer follows redirects. Before this release a
  provider's 307 or 308 to another host would have carried the caller's
  `x-api-key` and the whole prompt with it, because a cross-host redirect
  strips only a short list of headers and keeps the method and body. A 3xx
  from the provider now reaches the caller as a refusal with no usage and is
  charged zero (#316).
- A `send` error after the connection to the provider existed is now treated
  as an unknown outcome. Both the run and the unit reservation are retained
  and shown in `GET /v1/runs` (`retained`, `retained_usd`), the same way a
  cancelled call is kept since 1.0.3. Before this release such an error
  released the reservation, although the provider could have received the
  call and billed it. The response stays a 502 (#316).
- A request that cannot be built, or a connect error on the single hop
  (DNS, refused TCP, TLS handshake, connect timeout), still proves nothing
  was sent: it releases both reservations at zero and records one
  `dependency_failed` event at stage `send`, as before (#316).

## Upgrade notes and limits

- A provider outage that fails at connect time releases as before. A
  provider that accepts the connection and then fails leaves the call
  retained; each such call holds its estimate until reconciliation. There is
  still no admin reconciliation route, and retained reservations are
  process-local, so a restart forgets them together with the run ledger.
- A deployment that relied on the gateway following a provider redirect
  must point `TOKENFUSE_UPSTREAM` at the final address.
- Clean streams without final usage and usage preceding a body error remain
  under review (#308, #309). No claim of complete provider-charge accounting
  is made for these cases.
- The launchers need their own pin updates; tagging this repository does not
  change a running installation.
- The raft backend is optional and is compiled out of the shipped gateway
  image, as in earlier releases.
