# TokenFuse 1.20.3

A patch release with a fix to what the gateway reports. With `TOKENFUSE_AGENT_TOKENS=require`, a call with an unknown client key, or with no key, was refused with `401 agent_token_required` and left nothing on the shared event bus, so a key scan against a gateway in that mode was invisible to every consumer of the bus. The same two calls at a door that is not in require mode were already reported. They are now reported at the require door too. Upgrading is recommended for every deployment that sets `TOKENFUSE_AGENT_TOKENS=require` and has anything reading the bus.

It covers everything merged since v1.20.2: pull requests #491 and #492. Pull request #492 moved the README badge, the README examples and the compose pins to v1.20.2 after that tag existed. This release moves them to v1.20.3 in a post-tag pull request, once the tag and its images exist.

`compat/1.0.json` and `components.json` are unchanged since v1.20.2.

## Upgrade

Read this section before you change the image tag.

1. No configuration changes and no migration. Change the image tag.
2. The answer to the client is unchanged: the same `401` status, headers and body bytes as before for an unknown key, an unlisted key and no key. A client sees no difference.
3. What changes is on the bus. A gateway in require mode now writes an `identity_mismatch` event (severity high) for a call with an unknown key (reason `unknown_key`, with a `key_fingerprint` of `sha256:` and 16 hex digits, never the key) and for a call with no key (reason `missing_key`). If you alert on high `identity_mismatch` events, expect them from require-mode gateways where there were none. The volume is bounded by the limiter the open door already used: one event per source per minute, and sixty a minute for the gateway.
4. A key the gateway knows but the list does not name is still refused as before and is still not reported: it is not an unknown key, and its fingerprint would be a real secret's. The log warning still names its id.

## Security

- The refusal of an unknown or missing client key at the require door is on the event bus, as at the open door (#491, invariants 105 and 138). It was measured on a v1.20.1 gateway on 2026-10-28.

## Not measured

- The fix has not been run live yet. The new tests fail before the fix and pass after it, and hold the answer to the bytes `agenttoken::required_response` builds, but a live gateway in require mode, upgraded and scanned with unknown keys, is the run that follows this release.
- The MCP broker's own door writes nothing on a refused key. That is a recorded limitation (invariants 105 and 30), not covered by this release.
- A presented agent token that is refused is logged and is not on the bus at either door.
