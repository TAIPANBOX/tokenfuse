# TokenFuse 1.6.1

One fix: the MCP broker now works with MCP servers that keep a session,
which is the default for servers built on the official MCP Python SDK.

This is a patch release. It adds no route, no variable and no configuration,
and nothing frozen in `compat/1.0.json` moves. The umbrella crate and both
client SDKs move to 1.6.1 with no client behavior change.

## Fixed

- **The MCP broker keeps the session a stateful server opens (#360, invariant
  77).**
  - **The defect.** A server in the Python SDK's default mode opens a session
    on `initialize`, names it in an `Mcp-Session-Id` response header, and
    refuses any later message that does not carry it. The broker passed
    neither the id nor `MCP-Protocol-Version` along. So through the broker
    such a server answered `initialize` and then `400 Bad Request: Missing
    session ID` to `notifications/initialized`, `tools/list` and
    `tools/call`, over HTTP and over stdio. 1.6.0's own notes listed this
    under Not proven.
  - **Over HTTP the client holds the session, and the broker binds it.** The
    client receives the server's id behind a tag:
    `tf1.<tag>.<server's id>`. The tag is an HMAC under a key the broker
    draws at startup, computed over three things:
    - the upstream it was opened on;
    - the broker credential the call came with;
    - the id itself.

    A presented id is unwrapped only for that same upstream and that same
    credential. Any other id gets `404` and is never forwarded. That
    includes the server's raw id, an id for another named upstream
    (`X-Fuse-Mcp-Upstream`), and an id opened under another caller's key.
    A `404` is the answer that tells an MCP client to start a new session.
    The broker stores nothing. `MCP-Protocol-Version` is forwarded as the
    client sent it.
  - **Over stdio the broker holds the session itself**, because one process is
    one client. It keeps the server's id and the negotiated protocol version
    and sends both on every later message. A new `initialize` replaces them.
  - **A notification gets no JSON-RPC answer.** Before this release, a
    notification got `200` with a JSON-RPC error, and on a stateless server
    `bad upstream json: EOF`. Now an accepted notification is answered `202`
    with no body, and stdio writes nothing. A refused notification gets an
    error status. An upstream `404` on a session is relayed as `404`.
  - **Measured against real servers.** FastMCP on mcp 1.30.0 and MCPServer on
    mcp 2.3.0, both in default stateful mode. The SDK's own client now
    initializes, lists tools and calls one through the broker. Over stdio,
    four messages get three answers, all results. Stateless servers work as
    before, and their notifications now get `202`.

## Upgrade

- **Nothing to configure.**
- **A client that already handled `404` by re-initializing needs nothing
  new.** The same holds for one that ignores `Mcp-Session-Id`, if its server
  is stateless.

## Not proven

- **A broker restart or a second replica.** The key lives in the process, so
  either one answers `404` to every session the first one bound, and clients
  start new sessions. The stacks run one replica.
- **A broker with no credential configured.** A session is then bound to its
  upstream alone, and any caller holding the id can use it.
- **`DELETE` and `GET` on the broker.** Both answer `405`, which the
  specification allows. A session ends when the server expires it, and
  nothing the server sends outside a response reaches the client.
- **Re-initializing on stdio.** If a server forgets the session, the stdio
  client gets an error until it sends `initialize` again. The broker does not
  re-initialize for it.
- **Other MCP SDKs.** Only the two Python SDK versions above were tried.
