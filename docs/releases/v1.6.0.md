# TokenFuse 1.6.0

Two fixes.
- A gateway at a remote site now remembers what its runs have already spent
  after a restart or a hub migration. Before this release it could not see
  that spend through the hub's public entry.
- The MCP broker now speaks the streamable HTTP transport that current MCP
  servers require.

This is a minor release because it adds one Cloud route, `GET /v1/run-spend`.
Nothing frozen in `compat/1.0.json` moves, and a gateway or Cloud that does not
know the route behaves exactly as on 1.5.0. The umbrella crate and both client SDKs move to 1.6.0 with no client
behavior change.

## Fixed

- **A remote site seeds its runs' spend through a read scoped to that site
  (#356, invariant 75).**
  - **The defect.** A gateway seeds each run's Cloud-known spend at startup
    (invariant 70), so a restart does not reset a run's budget accounting to
    zero. It read that spend with `GET /v1/runs`, which lists the whole org.
    The hub entry that remote sites reach the Cloud through answers that path
    404 on purpose. A remote site's gateway therefore seeded nothing, and
    every run started at zero after a restart.
  - **Measured 2026-10-05 on a hub migration.** Run `mig-flint` had 2566 uUSD
    at the hub and a 4500 budget. A call estimated at about 2550 passed at the
    remote site. The same call at the same budget got 402 at home, where the
    gateway reaches the Cloud directly.
  - **The new route.** The Cloud now answers `GET /v1/run-spend?since_millis=`.
    It answers only an org key bound to a site, of any role, and only about
    that site's own runs. Each row has three fields: `run_id`,
    `spent_microusd` and `killed`. Every other credential gets 403, and no key
    gets 401.
  - **What the gateway does.** It asks this route first. It falls back to
    `/v1/runs` only on 403 (a key bound to no site, as in-cluster gateways
    have) or 404 (an older Cloud).

- **The MCP broker speaks streamable HTTP to its upstream (#358, invariant
  76).**
  - **The defect.** The broker forwarded `tools/*` calls with reqwest's
    default `accept: */*` and read every answer as one JSON document.
    - The MCP Python SDK 1.x answered 406 to every broker request.
    - The SDK 2.x by default answers as `text/event-stream`, which failed as
      `bad upstream json`.
  - **The headers sent.** The broker now sends `Accept: application/json,
    text/event-stream`, the same value the `mcp-scan` client already sent.
  - **How an answer is read.** An answer is read by its content type. An
    event stream goes through the existing WHATWG splitter (invariant 55), and
    the reply is the first JSON-RPC response that carries the request's id.
    Any other content type is read as JSON, as before.
  - **The checks.** A streamed reply goes through the same poisoning scan,
    rug-pull diff and DLP redaction as a JSON reply.
  - **Measured against real servers.** In stateless mode, mcp 1.30.0 and
    2.3.0 now answer `initialize`, `tools/list` and `tools/call` through the
    broker. Before the fix they answered 406 or `bad upstream json`.

## Upgrade

- **Nothing to configure.** A site's key from `hub/add-site.sh` is already
  bound to its site.
- **Through a hub entry, both halves are needed.** The entry must route the new
  path (stack-k8s#125, eight routes), and the Cloud and the gateway must both
  be on 1.6.0. With either half missing, a restarted site gateway seeds
  nothing, exactly as on 1.5.0. One WARN line at startup says so.
- **In-cluster gateways are unchanged.** They get 403 from the new route and
  keep reading `/v1/runs`.

## Not proven

- **MCP sessions (#358).** The broker neither sends nor relays
  `Mcp-Session-Id`, so a server in the SDK's default stateful mode still fails
  every call after `initialize` with 400.
- **`MCP-Protocol-Version` (#358).** The broker does not send it.
- **A stream that stays open (#358).** The broker buffers the whole streamed
  body with no timeout, so a server that keeps the stream open holds the call.
- **Other MCP SDKs (#358).** Only the Python SDK was tried.

- **No live hub run.** The release was proven locally with real binaries
  behind a stand-in for the entry that reads the manifest's route set: a
  restarted site gateway got 402 where 1.5.0's got 200, at the same Cloud
  state and budget. It was not run behind the real Caddy entry or on a live
  hub.
- **A run pushed by two sites.** A run's site is "last non-empty wins", so the
  site that pushed it first is not told its spend.
- **A hub migration.** The site's new key must carry the same site name the old
  hub recorded.
