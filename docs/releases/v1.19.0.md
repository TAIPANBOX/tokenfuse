# TokenFuse 1.19.0

A minor release, and a security-default release. An unconfigured gateway and an unconfigured MCP broker now enforce what they advertise, where v1.18.0 started in observation. A gateway that listens beyond loopback with nothing authenticating its callers now refuses to start. Agent tokens get a named static-key allow-list, and the policy plane is told which agent token admitted a call. The control plane tightens its browser, credential and key handling.

It covers everything merged since v1.18.0: pull requests #465, #467, #468, #469, #470 and #471. #466 was closed and its test fix travelled in #465.

No frozen name in `compat/1.0.json` is removed or renamed. The additions are new names, a new response header, new decide-request members and a new health-detail field.

## Upgrade

Read this section before you change the image tag. Most of the items below change behaviour for a deployment that set nothing.

1. **The gateway and the MCP broker are governed by default (`TOKENFUSE_PROFILE`, invariant 136).** Unset, the profile is `governed`. It sets the following defaults, for every variable you leave unset:
   - `TOKENFUSE_MODE` enforces budgets. It was shadow.
   - The agent firewall enforces, unless `TOKENFUSE_FIREWALL` or a policy file names a mode.
   - A firewall policy file that names no `mode` enforces. It was off.
   - The policy hook (`TOKENFUSE_WARDRYX_MODE`) enforces once `TOKENFUSE_WARDRYX_URL` is set, with a closed failmode. Without a URL it stays off.
   - Declassification is closed unless `TOKENFUSE_DECLASSIFY_KEY` is set.
   - The five admin routes need `TOKENFUSE_ADMIN_KEYS` even on loopback.

   **What to do:** to keep v1.18.0 behaviour exactly, set `TOKENFUSE_PROFILE=observe`. That profile prints one startup line saying it enforces nothing you have not set explicitly. Any variable you set yourself wins over the profile in either direction.

2. **A gateway that listens beyond loopback with no client authentication refuses to start (invariant 137).** Under `governed`, a bind address that is not loopback, with neither `TOKENFUSE_CLIENT_KEYS` nor `TOKENFUSE_AGENT_TOKENS` set, exits with code 2 before it binds. The shipped image binds `0.0.0.0`, so an unconfigured container stops at start.

   **What to do:** set `TOKENFUSE_CLIENT_KEYS`, or `TOKENFUSE_AGENT_TOKENS`, or `TOKENFUSE_PROFILE=observe`. A loopback bind starts with no client keys, as before.

3. **Every command and compose service in the quickstart names one of those three ways out.** The headline command in the README and the compose gateway service set `TOKENFUSE_PROFILE=observe` for an unauthenticated trial. A copy of an older quickstart without it will stop at start, for item 2.

4. **The policy hook and the firewall in an unconfigured deployment (invariants 117, 136).** With `TOKENFUSE_WARDRYX_MODE=enforce` and no failmode, the failmode is `closed`. An enforcing policy hook that cannot reach its policy plane now refuses the calls it would have judged. Before, it allowed them. A deployment that set no failmode changes with this item.

   **What to do:** set `TOKENFUSE_WARDRYX_FAILMODE=open` only if you want an unreachable policy plane to allow calls. A launcher that set no failmode changes with this item.

5. **A caller can no longer raise an open run's budget (invariant 135).** `x-fuse-budget-usd` sets a run's budget when the run opens. On later calls it can lower the budget and never raise it. A refused raise is named on the answer as `x-fuse-budget: raise-refused; kept=<usd>`, on the 402 it causes as well. The operator's ceiling (`TOKENFUSE_MAX_RUN_BUDGET_USD`) still bounds the figure a run opens at.

   **What to do:** an agent that raised its own budget mid-run must open a new run id, or have an operator set a Cloud budget for the run. A retained reservation is no longer widened by a caller's next call. It comes back through its closure (invariant 89) or through an operator's Cloud budget.

6. **Agent tokens: `require` keeps a named static-key list (invariants 138, 139).** `TOKENFUSE_AGENT_TOKENS=require` used to refuse every static key. It now admits a static key only when its key id is named in `TOKENFUSE_AGENT_TOKENS_STATIC_KEYS` (gateway) or `TOKENFUSE_MCP_AGENT_TOKENS_STATIC_KEYS` (broker). The gateway refuses to start if a listed id is not in `TOKENFUSE_CLIENT_KEYS`, and the broker refuses the same way against `TOKENFUSE_MCP_KEYS`.

   **What to do:** nothing, if you already run `require` with no static keys, or `accept`. To keep a client that cannot sign a proof, list its key id. Move each client to an agent token, then remove it from the list.

7. **The policy plane is told the agent token that admitted a call (invariant 140).** On a call an agent token admitted, the decide request carries `agent_token` (the compact token, as presented) and `agent_dpop_proof` (the proof, as presented), each bounded at 4 KiB. Neither is sent on a static-key call, and neither is logged. A policy plane that ignores unknown members is unaffected. A policy plane that verifies the proof can cap a relayed token's use at the proof's freshness window. This repository does not test a policy plane that verifies it.

8. **Device tokens are stored as digests in the state file (invariants 132, 133).** The control plane keys its paired devices by SHA-256, so the state file no longer holds a live device token. Org keys are held by digest in memory. The first save after the upgrade rewrites the device map in digest form. This is one way: a v1.18.0 binary cannot authenticate devices from the new state file.

   **What to do:** to roll back, pair each device again. A device request signed before the restart, or in the same second as it, is refused once. The device retries with a fresh timestamp.

9. **Device nonces survive a restart (invariant 132).** The nonces a device has used are saved and reloaded, so a request signed before a restart cannot be replayed after it.

10. **The control plane answers only named browser origins (invariant 131).** Until now every response carried `Access-Control-Allow-Origin: *`. Now the control plane answers loopback origins only, unless `TOKENFUSE_CLOUD_CORS_ORIGINS` names others. Each entry is an exact origin, such as `https://dashboard.example.com`. A set value replaces the loopback default. A malformed entry or a wildcard refuses to start, with exit code 2.

    **What to do:** a dashboard served from a non-loopback origin stops being answered until you name its origin in `TOKENFUSE_CLOUD_CORS_ORIGINS`.

11. **The dashboard takes its key from the URL fragment (invariant 133).** A dashboard link should now carry the key after `#key=`, which the browser never sends to the server. A link with `?key=` still works. The key is removed from the address bar on arrival.

12. **The audit manifest refuses a keyryx key id that is not the key's RFC 7638 thumbprint (invariant 130, #467).** An audit manifest signed through keyryx is refused with a 503 when the key id keyryx returns is not the thumbprint of the key that signed. Before, any non-empty key id was accepted, which let a manifest name the wrong key for an auditor.

    **What to do:** if your manifest now returns 503 with that reason, check that keyryx names the signing key by its thumbprint. ML-DSA keys were already refused, as before.

## Added

- `TOKENFUSE_PROFILE` (`governed` or `observe`), with a `profile` field on `GET /healthz?detail=1` and a `governance` startup line naming each governed setting and whether the profile or your environment decided it (invariant 136).
- `TOKENFUSE_AGENT_TOKENS_STATIC_KEYS` and `TOKENFUSE_MCP_AGENT_TOKENS_STATIC_KEYS` (invariants 138, 139).
- `agent_token` and `agent_dpop_proof` on the policy-plane decide request, on a token-admitted call only (invariant 140).
- `TOKENFUSE_CLOUD_CORS_ORIGINS` (invariant 131).
- The response header `x-fuse-budget`, present only when a raise was refused (invariant 135). It is registered as an additive response header in `compat/1.0.json`.

## Changed

- An unconfigured broker's policy hook follows the profile: enforce with a closed failmode once `TOKENFUSE_WARDRYX_URL` is set, otherwise off, marked `no-url` in its governance line.
- The decision cache of the policy plane is keyed on the identity source as well as the agent and the tools. A verdict reached on an agent token is not served to a static-key call (invariant 124).
- Client keys are stored and compared as digests, and the declassify key is compared in constant time (invariant 134). Nothing to do for an operator.

## Other changes

- The CI test for the drain of the control-plane retry queue was made deterministic (#465, from #466). Test support only.
- #465 moved the README badge, the README examples and the compose pins to v1.18.0, after that tag existed. This release moves them to v1.19.0 in a post-tag pull request, once the tag and its images exist.

## Not in this release

- The policy plane's proof verification is outside this repository. This release sends the agent's proof to the policy plane. It does not check that anything verifies it.
