# TokenFuse 1.20.0

A minor release. A gateway reached at more than one address can now accept a delegation proof or an MCP proof addressed to any of the public origins the operator lists. Before, a proof had to name the one origin in `TOKENFUSE_DELEGATION_URL` or `TOKENFUSE_MCP_PROOF_URL`, so a caller reaching the gateway at another address was refused with `401`. The two new variables, `TOKENFUSE_DELEGATION_ORIGINS` and `TOKENFUSE_MCP_PROOF_ORIGINS`, are read beside the single-origin ones. A deployment that names one origin sees no change.

It covers everything merged since v1.19.0: pull request #474, with the dependency and test-only changes that came with it. Pull request #473 moved the README badge, the README examples and the compose pins to v1.19.0 after that tag existed. This release moves them to v1.20.0 in a post-tag pull request, once the tag and its images exist.

`compat/1.0.json` is unchanged since v1.19.0. The two new variables are configuration, declared in `components.json`.

## Upgrade

Read this section before you change the image tag.

1. A deployment that names one origin and sends proofs for it keeps working unchanged.
2. A list with an entry that is not an origin, a trailing comma included, now refuses to start. Before, the broker read the whole value as one origin and refused every proof.
3. `TOKENFUSE_DELEGATION_URL` and `TOKENFUSE_MCP_PROOF_URL` must now be an origin, `scheme://host[:port]` with nothing after the port but an optional `/`. A value with a path, for example a gateway published under `https://host/tokenfuse`, used to be joined to the route's path and now refuses to start, naming the variable. The stack launchers set an origin without a path and are not affected.

## Changed

- The delegation door, the agent-token door and the MCP broker's proof door take a list of public origins. `TOKENFUSE_DELEGATION_ORIGINS` and `TOKENFUSE_MCP_PROOF_ORIGINS` are read beside the existing single-origin variables, and a proof is accepted when its `htu` names any of them at the route's path (invariant 141).
- A proof whose `htu` carries a fragment is refused at every door. RFC 9449 section 4.3 says an `htu` names a URI without one; the verifier used to trim it away.
- An origin is compared in the form wardryx's agent-token door uses: scheme and host in lower case, the default port written out. `https://host/path` and `https://HOST:443/path` name one origin.

## Other changes

- `rust_decimal` 1.43.0 in `crates/cluster`. The bump takes `rkyv` 0.7 out of that lockfile, which removes the advisory RUSTSEC-2026-0235 from its build graph.
- Test-only changes: the MCP door's origin tests carry names of their own, and a test module drops an unused import and counts the new tests.

## Not proven

- The list is read at startup, so a change to it needs a restart.
- The `rkyv` advisory entry in `.cargo/audit.toml` matches nothing since the `rust_decimal` 1.43.0 bump. It stays for a follow-up, because removing it changes teeth cases that CI has not run against the new config.
- The stack launchers in this estate still set one origin. A deployment reached at a second address stays refused until its launcher names that address in `TOKENFUSE_DELEGATION_ORIGINS` or `TOKENFUSE_MCP_PROOF_ORIGINS`.
